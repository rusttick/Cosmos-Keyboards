# Scan procedure: the `/scan3` capture protocol

This is the process document: for each movement in the capture session, what position the hand is in, what's said to the user, what's recorded, what's calculated from it, and — the piece that didn't exist in any prior doc — how the software knows a step is _done_ well enough to move on, versus needs to be repeated.

`scanning.md` established _what_ five signals we want (bone length, neutral pose, full ROM, comfortable ROM, cross-finger interaction) and why. `problems.md` established the biomechanical grounding. `pre-development-work.md`, `key_point_selection.md`, and `scan_utility_evaluation.md` established what those signals feed into. This doc is the layer in between: the literal, scriptable sequence of instructions and completion checks a developer can implement as `/scan3`, forked from `/scan`.

## What this doc supersedes or drops

A working session (this doc is the output of it) settled several things that earlier docs left open or got wrong. Stated here explicitly so they aren't re-litigated or accidentally re-added during implementation:

- **No ChArUco/checkerboard, no printed reference sheet.** The `/scan2` calibration approach (`chessboardDetector.ts`, `reconstruction.ts`) reconstructs 3D positions by assuming the hand is coplanar with the calibration board (`HAND_DEPTH = 0` in `cameraToMarkerPoint`) — valid only for a flat hand pressed against a plane, not for the curled/moving poses most of this protocol needs. It also depends on a hardcoded, uncalibrated camera focal length (`fx=fy=1000` in `reconstruction.ts`), a second error source independent of the planarity problem. Scale calibration is done by caliper instead ("Pre-scan input: caliper calibration" below).
- **No wrist/forearm capture.** `scanning.md`'s own conclusion stands: no desk fixture constrains a forearm well enough, and MediaPipe has no elbow landmark to check against anyway. Wrist/tenting placement is a manual `SolvedHand.position` UI concern, entirely separate from this capture protocol.
- **No bilateral (both-hands-at-once) capture, except Phase 2.** `/scan` today records both hands simultaneously. This protocol runs **one hand at a time**, sequentially, for the whole session — chosen over the bilateral default because several phases depend on clean single-finger isolation, which bimanual/mirror-movement coupling is a real, untested risk to (see "Open items" below). Phase 2 (neutral/rest hold) is the one deliberate exception: it isolates nothing, and the relative position/orientation between the two hands at rest is itself a real design input that only exists if both hands are captured together.
- **No hard-press "maximal" abduction tier.** Pressing all digits down hard produces a passive splay driven by shoulder/proximal muscles transmitting load through the desk — mechanically real, but not the same phenomenon as active, voluntary abduction, and explicitly excluded by the active-vs-passive-ROM principle `scanning.md` §3 already establishes. Abduction is captured as a single active-ROM tier, not two (see Phase 4 below).
- **Drag and block trials are unified into one phase**, not two, because true single-finger isolation without fixturing is unrealistic (the user will always get some cross-finger motion) — the block condition's "hold at discrete targets" instruction assumed a precision of static control that isn't achievable unfixtured either. Both signals are now extracted from one retained, freely-explored paired-motion trajectory (see Phase 5 below).

## Camera constraint: immobilized, not a fixed angle

The one hard requirement is that the camera doesn't move once the session starts — no repositioning between phases. Its actual placement is deliberately **not** specified: an overhead mount, a laptop propped at some awkward angle to get height, a tripod across the desk at 45°, whatever the user can manage — all of it above the desk, generally pointed down at it. Locking the protocol to one specific angle (the way an earlier draft of this doc did, deriving everything from a 45°-across-the-desk tripod) would make the instructions wrong for anyone whose real setup differs, which is most people. Two different kinds of instruction follow from this, and it matters which one applies to a given phase:

- **Desk-contact-anchored instructions** ("palm down, flat on the desk," "dorsum resting on the desk, palm up") don't depend on camera angle at all — they're about mechanical bracing and stability, not imaging. Phases where the desk interaction is the point (Phase 2's rest hold, Phase 4's braced neighbors) should be specified this way and left alone regardless of camera placement.
- **Imaging-direction instructions** ("keep this motion out of the depth axis," "orient so this arc stays in the camera's view plane") depend on where the camera actually is, which varies per user and per setup and isn't something this doc can hardcode a direction for. These need to be stated _relative to the camera_, not in absolute desk/world coordinates — and made concrete via the calibration step below, rather than assumed from one imagined tripod position.

### Camera-orientation calibration gesture

Borrowed from the mutually-orthogonal three-finger posture used to indicate a coordinate frame in physics/engineering (thumb, index, and middle finger extended pairwise perpendicular to each other) — a quick, no-hardware way to let the software discover the actual camera geometry for this session instead of assuming one.

- **Instruction:** "form the three-finger axis pose [thumb, index, middle mutually perpendicular], then point your index finger directly at the camera and hold for a couple seconds."
- **Why this works, regardless of the camera's real angle:** by construction, the other two fingers (thumb and middle) are perpendicular to whichever direction is pointed at the camera. If index is aimed along the camera's sightline, thumb and middle are — by definition of the gesture, not by any assumption about mounting angle — the two directions perpendicular to that sightline, i.e. the two directions least subject to foreshortening for _this specific, unknown_ camera placement. This is the general replacement for the old doc's "x-axis is always visible" claim: instead of assuming a placement that guarantees a particular world axis is well-imaged, have the user physically construct two directions guaranteed well-imaged for whatever placement they actually have.
- **What's calculated:** the three-finger gesture's own basis (already computable from the same bone-direction/`makeBasis` math `hand.ts` uses for its per-frame frame-fitting) is recorded as the session's camera-relative reference frame. Later phases whose completion or scoring cares about foreshortening (Phase 1's rotation coverage, primarily) can score against this measured frame instead of an assumed one.
- **Completion criteria:** a couple seconds of confidence-passing frames with the gesture detected as sufficiently orthogonal (the three bone-direction vectors' pairwise angles within some tolerance of 90°, e.g. ±15°) and sufficiently stable (low velocity, similar to Phase 2's still-window check).
- **Retry:** gesture not detected as orthogonal enough, or held for insufficient duration → repeat with a reminder to keep the three fingers genuinely perpendicular, not just spread apart.
- **Left to the implementer:** the exact derivation of "how foreshortened is direction D, given this calibration" from the recorded basis is a small piece of vector math (project D onto the sightline vs. the perpendicular plane), not specified numerically here — same level of detail this doc leaves to other extraction steps.

## Pre-scan input: caliper calibration

Done once, before any camera capture, no vision involved.

- **What to measure:** middle finger (longest, so measurement-noise-to-length ratio is smallest), finger fully extended and flat, calipers oriented along the finger's length axis (never pinching girth/thickness — that measures soft tissue, not skeletal length).
- **Landmark points:** fingertip pad center (matching where MediaPipe places the tip landmark, not the nail's edge), and the **centroid of the base crease cluster** — the flexion crease dividing the finger from the palm is usually several close, non-identical lines; take the center of that cluster, not one arbitrarily chosen line. This is deliberately consistent with what MediaPipe's own landmark convention approximates: its "joint" landmarks were trained against visually annotated skin creases, not idealized skeletal joint centers, so a centroid-of-cluster measurement is the closer match, not a compromise.
- **How it's applied:** not a one-shot post-hoc correction. `scaleFactor = caliperValue / (pooled middle-finger MCP→PIP + PIP→DIP + DIP→tip length)` is recomputed continuously as the pooled bone-length estimate updates through the session (same incremental recompute `Recording.svelte` already does for `calculateJoints`), converging as more frames accumulate rather than being locked from an early, noisier estimate. This factor is applied uniformly to every bone in the hand — valid only because relative bone-length _ratios_ across fingers are already established as trustworthy (`problems.md` §2); only the single global scale is being corrected.
- **Completion criteria:** a plausible numeric value has been entered (sanity range, e.g. 60–120mm for an adult middle finger). Implausible values prompt a re-measurement, not a silent accept.

## Session structure

- One hand at a time, start to finish, then repeat the whole sequence for the other hand — except Phase 2, which is bilateral (see Phase 2 for why).
- Digit order, used consistently across every per-finger phase: **thumb → index → middle → ring → pinky.**
- Phase order per hand: 1 (bone length, optional) → 2 (neutral, bilateral, initial capture) → 3 (flexion ROM, per finger) → 4 (abduction, per finger) → 5 (paired sweep, per finger pair) → 6 (thumb CMC capture).
- Phase 6 excludes the thumb from Phases 3–5's per-finger/per-pair loops — the thumb's joint structure doesn't match the finger-shaped instructions those phases use (see Phase 6 for why), so it gets its own dedicated phase instead of being folded into theirs.
- Phase 2 can additionally be re-run any number of times after the full scan, independently and bilaterally, to capture further named resting postures — see Phase 2's standalone mini-flow.

## Phases

Every phase shares one baseline quality gate, applied continuously, not just described once: reject frames below MediaPipe's existing 0.7 confidence threshold; if a segment's accepted-frame yield is too low, that segment fails its completion check regardless of any phase-specific criterion below, and is retried.

### Phase 1 — Bone-length refinement (optional, low priority)

- **Position:** hand flat, fingers spread, palm toward camera, rotating slowly through a small arc.
- **Instruction:** "hold your hand flat and open, and slowly rotate it side to side."
- **Captured:** per-frame bone vectors, weighted by how close each bone was to perpendicular to the camera that frame (foreshortening is worst when a bone points toward/away from the lens).
- **Calculated:** perpendicularity-weighted mean bone length per segment — feeds the same pooled estimate the caliper scale factor ("Pre-scan input" above) divides into.
- **Completion criteria:** ≥100 accepted frames, spanning a minimum rotation arc (track the hand-plane normal's angle relative to the camera across frames; require some minimum swept angle, e.g. 30°, so "rotation" wasn't skipped).
- **Retry:** insufficient frame count or insufficient rotation coverage.

### Phase 2 — Neutral/rest hold

This is the one exception to the one-hand-at-a-time rule (see "What this doc supersedes or drops" above), and it's bilateral by requirement, not just by permission — the relative position and orientation _between_ the two hands at rest is itself a real, useful design input (natural resting separation and mutual tenting angle), and that relationship only exists in a frame where both hands are visible together. Scanning each hand alone, even in a matching named orientation, cannot recover it. Every other phase's one-hand-at-a-time rule stands: this exception exists because Phase 2 has no isolation to protect (nothing here asks any finger to move independently of anything else), unlike Phases 3–6.

- **Position:** both hands resting together however falls naturally, no prescribed orientation for the initial capture.
- **Instruction:** "let both hands fall relaxed, as if resting on a desk together, and hold still for a few seconds."
- **Captured:** per-frame joint angles for both hands throughout the hold, plus each hand's own local basis (`makeBasis`) per frame — needed for the relative-transform calculation below.
- **Calculated:**
  - **Neutral angle per joint, per hand** — same still-window extraction as before: auto-select the lowest-variance sub-window (discarding at least the first ~0.5s while the hands settle), average joint angles over it.
  - **Relative transform between the hands** — using the same synchronized sub-window, compute the right hand's basis relative to the left hand's: separation distance and relative rotation (splay/mutual tenting angle). Separation distance is well-grounded here even though absolute monocular scale is normally the weak point (`problems.md` §2), because each hand's own caliper-corrected scale (from its own full scan) anchors real-world distance in the same shot — no fresh scale estimate needed.
- **Completion criteria:** a sub-window of minimum duration (e.g. 1s) where _both_ hands simultaneously satisfy the velocity threshold, with enough accepted frames for both, found somewhere in the hold — a synchronized snapshot of both hands resting together, not two hands independently settling and stitched together after the fact.
- **Retry:** no window found where both hands are simultaneously still for long enough within the allotted hold time (e.g. 5s) → ask the user to hold more still, possibly lengthening the window.

**Resting posture as a repeatable, independent capture, not a one-shot fixed reference.** More than one comfortable resting posture is possible and meaningfully different depending on the tenting/wrist configuration a design attempt is exploring (flat/low-tent, high-tent/vertical, inverted, "holding a ball," fingers pointed back toward the chest, or anything else) — gravity pulls the hands into a different passive equilibrium shape at zero voluntary effort depending on orientation, so there is no single universal "the" neutral pose. This capture is therefore decoupled from the rest of the session:

- The **full scan** (Phases 1, 3, 4, 5, 6, plus one initial Phase 2 capture) is done once, producing one stored `HandData` record with bone lengths, ROM, enslaving, and thumb CMC data.
- A separate, standalone **resting-posture mini-flow** can be launched at any later time, independent of redoing the full scan: it loads the existing stored record (same `localStorage`/export pattern `/scan` already uses), runs just the bilateral capture and calculation above for whatever orientation is currently being held, and writes the result back into that same record under a user-chosen label (e.g. "flat," "high-tent," "ball") — either adding a new named entry or overwriting an existing one with that label.
- This mini-flow needs none of the rest of the pipeline's state — not the caliper scale factor (angles are scale-invariant; only bone lengths need that correction), not the camera-orientation calibration gesture (that exists for foreshortening-sensitive completion checks elsewhere, irrelevant to a simple still-window extraction), not any ROM/enslaving/thumb data. It is genuinely self-contained, which is what makes "capture the full scan once, then the resting posture as many times as desired" workable rather than just convenient.
- No fixed enum of labels is needed — the mini-flow just takes free-text, and whatever names accumulate over time (however many postures get captured) become the available options wherever a later placement/tenting UI lets someone choose which resting posture to design around.

### Phase 3 — Per-finger flexion/extension ROM, two tiers

- **Position:** palm facing the camera — inherently a camera-relative instruction, not tied to any assumed mounting angle — one finger at a time in digit order.
- **Instruction, per finger:** "move [finger] to your comfortable maximum, without strain, and hold" (tier 1) → "now push it to your true limit, and hold" (tier 2). Each tier repeated 3× (flex/extend cycles).
- **Captured:** per-frame joint angle for the active finger's MCP-Z, PIP-Z, **and DIP-Z** — DIP is retained too, not discarded, even though it isn't independently instructed (it's along for the ride, mechanically driven by PIP flexion; see below).
- **Calculated:** tier 1's held pose gets the same still-window extraction as Phase 2 → **comfortable-ROM bound** per joint. Tier 2's full sweep, with per-frame angles retained (not pooled), gives **min/max = active full ROM** per joint, for MCP, PIP, _and_ DIP. The SVD singular-value ratio already computed and discarded in `fitNorms` (`hand.ts:215-243`) is surfaced here too, as a per-joint axis-fit-confidence number. **DIP-vs-PIP coupling**: rather than assuming DIP tracks PIP at some literature-derived ratio, fit it — regress the retained DIP-Z against PIP-Z across the tier 2 sweep, per finger. This is the same technique already used elsewhere in this doc for the enslaving coefficient `E[i][j]` and the thumb's conjunct-rotation coupling, run here on data the phase is already collecting for other reasons, at essentially no added capture cost. Fitting it per finger is the point: a hand can have (and does, per direct report) a large DIP range on one finger and almost none on another — a single borrowed ratio would flatten exactly the variation this is meant to capture. A near-zero fitted slope for a given finger is a valid result, not a failure of the fit.
- **Completion criteria (plateau detection):** track the running min and max angle observed across repetitions, for **all three** joints (MCP, PIP, DIP), not just the phase's nominal target. Completion = the last 2 repetitions each failed to extend _any_ of the three observed ranges by more than a small threshold (e.g. 2°). Requiring DIP's own extremum to converge too (not just PIP's) matters most for a finger with a small-but-real DIP range, which could otherwise plateau on PIP well before DIP's narrower range has been adequately sampled for the coupling fit.
- **Retry:** if the requested rep count (3) finishes without the plateau condition being met for all three joints, prompt for more reps rather than accepting an unconverged bound.

### Phase 4 — Braced abduction, single active tier

- **Position:** palm down, flat on the desk. Four digits maintain **light** contact with the desk (just enough to prevent them dragging along with the target finger — not pressed hard; hard pressing invokes the passive-splay mechanism described in the scope section above and must be avoided throughout, not varied for tiering). One digit at a time is the active/target finger, in digit order.
- **Instruction, per finger:** "press your other four fingers down gently, and move [finger] back and forth: press down, lift in an arc, swing over to the other side, press down again — like reaching between two keys on a row. Keep it light and comfortable, not forced."
- **Captured:** per-frame abduction angle (MCP-Y) for the target finger throughout the press-lift-arc-press cycles. Press-contact instants (near-zero velocity, fingertip near desk height) are a naturally self-marking segmentation cue — cleaner than a freeform held-window, since the desk contact itself verifies the finger was momentarily stationary.
- **Calculated:** abduction angle sampled at each press-contact instant; min/max across cycles = **active abduction ROM**, single tier (no comfortable/full split — see scope section above for why).
- **Completion criteria (plateau detection):** same pattern as Phase 3's full-ROM tier — min/max stop growing across the last 2 press cycles.
- **Retry:** plateau not reached within the requested cycle count → more cycles requested.

### Phase 5 — Paired free-motion sweep (enslaving + blocking, unified)

Run once per finger pair of interest, for each of the two planes independently (flexion-plane pairs and abduction-plane pairs are separate trials, since a hand can have very different coupling strength in each — see "Open items").

- **Position:** hand held naturally in the air, no bracing, no fixturing, fingers not touching anything or each other.
- **Instruction, per pair (i, j):** "move fingers [i] and [j] together, however feels natural — sometimes moving mostly one while relaxing the other, sometimes exploring both together. Try to cover as much of the range as you can, in as many combinations as you can, over about 20-30 seconds."
- **Captured:** per-frame angle time series for both fingers throughout, in the relevant plane (flexion-plane trial: both fingers' MCP/PIP-Z; abduction-plane trial: both fingers' MCP-Y).
- **Calculated, from the same retained trajectory:**
  - **Enslaving coefficient** `E[i][j] ≈ Δθ_j/Δθ_i`, fit by regression over whichever sub-segments of the trajectory have i's excursion dominating j's (the "mostly one, relaxed other" portions of the freeform motion satisfy this without needing a separately-instructed condition).
  - **Prohibited-region boundary**: bin the `(θ_i, θ_j)` space into a grid; the boundary is wherever the trajectory, despite otherwise broad coverage, never visited a region — a measured gap, not a modeled one. Apply a wider confidence-margin filter here specifically, since tracking is weakest exactly at a blocking boundary (closely-spaced/overlapping fingers).
- **Completion criteria (coverage-grid detection):** bin the observed `(θ_i, θ_j)` samples into a grid spanning each finger's already-established ROM (from Phases 3/4). Completion = a minimum fraction of grid cells (e.g. 70%) have at least one confidence-passing sample. Live UI feedback should highlight unvisited cells so the user knows which combinations still need exploring — this is a coverage problem, not a duration problem, so the completion signal should be coverage-driven, not just a fixed timer.
- **Retry:** coverage threshold not met after the initial time-box → continue the same trial (not restart from zero — retain what's already covered) with guidance toward the specific unfilled regions.

### Phase 6 — Thumb CMC capture

This phase exists because getting it right is the actual point of this whole project. The current model fixes the thumb's base joint (CMC, joint index 0 in the existing `Joint`/`degree` scheme) at 0 DOF — a deliberate simplification, not a bug — which means whatever thumb workspace gets computed today is a cone anchored at a fixed orientation, not a genuine opposition arc (`problems.md` §2). That's the single biggest known gap between this model and reality, and it's exactly why Dactyl-derived thumb clusters end up placed by guesswork rather than measurement. Phases 3–5's finger-shaped instructions don't fit the thumb's joint structure, so the thumb is excluded from their per-finger/per-pair loops and captured here instead.

**Anatomy, and why the data problem is smaller than it looks:** the CMC is a saddle joint with two actively-driven rotations — flexion-extension and abduction-adduction — plus a third, **conjunct** axial rotation that isn't independently muscle-driven at all. It happens automatically as a mechanical consequence of the saddle surfaces sliding against each other during combined flexion+abduction, and it's specifically what makes true opposition (thumb pad rotating to face the fingertips) possible rather than just the thumb swinging closer to them. MediaPipe already tracks a dedicated landmark for this joint (landmark 1, `THUMB_CMC`) every frame — the fixed-0-DOF assumption is a choice in `fitNorms`/`calculateJoints`'s DOF-assignment table, not a sensing limitation. The needed code change is to stop assigning `degree: 0` to the thumb's joint 0 and fit its axis/range from data the same way every other joint already is fit.

**Orientation is much less constrained here than for the finger phases.** Thumb tracking holds up across palm-up, palm-down, and most other orientations, unlike the finger phases (where palm-up flexion was noted as noisier, though not disqualifying). What still matters is minimizing _self-occlusion_ during the specific motions below — a separate concern from general tracking robustness, handled by the multi-orientation approach in both sub-phases.

#### 6a — CMC-isolated outer sweep

- **Position:** MCP and IP joints held straight/extended throughout — the thumb moves only at its base, like a rigid rod pivoting at the CMC. Whatever orientation keeps the thumb clearly visible (not tracking-quality-constrained, per above).
- **Instruction:** "keep your thumb straight, and sweep it through its full comfortable range from the base, like swinging a stiff rod."
- **Captured:** per-frame CMC bone-direction vector throughout the sweep.
- **Calculated:** CMC's flexion-extension and abduction-adduction range fit via PCA/SVD on the observed motion (the same `fitNorms` method already used for every other joint, applied here for the first time to joint 0) — the _outer boundary_ of the thumb's reach, independent of any contribution from curling the tip joints.
- **Completion criteria (plateau detection, with a false-plateau guard):** same running-extremum pattern as Phases 3/4, but plateau detection alone can't distinguish "the joint genuinely stopped" from "confidence collapsed as the thumb rotated out of view, silently truncating the sweep." So: only accept the plateau if confidence/frame-yield stayed healthy right up to the apparent extreme. If yield was dropping as the extremum was approached, that's an occlusion-truncated pseudo-plateau, not a real limit.
- **Retry:** plateau not reached within the requested cycle count → more cycles, same as Phases 3/4. A _false_ plateau (yield-collapse pattern detected) → retry in a different orientation, not more cycles in the same pose — more time won't fix a region the camera structurally can't see from here.
- **Multi-orientation:** default to two orientations roughly 90° apart (the same "two viewpoints ~90° apart" idea `scanning.md` already uses elsewhere), rather than waiting for a false-plateau failure to trigger the first switch, since thumb self-occlusion is a known, not hypothetical, weakness (`problems.md` §2). Let the false-plateau guard decide if a third orientation is actually needed.

#### 6b — Freeform coverage sweep

- **Position:** no scripted target postures at all.
- **Instruction:** "move your thumb through as much of its comfortable reachable space as feels natural — not just toward your fingertips, in as many directions as you can."
- **Captured:** per-frame CMC (and MCP/IP) angles throughout, unconstrained.
- **Calculated:**
  - **Conjunct-rotation coupling**: regress the observed axial twist against the two driven angles (flexion, abduction) across the trajectory — the CMC analogue of `E[i][j]`, but fit within one joint's three rotations instead of across two fingers. Not elicited as its own instruction, since it isn't independently controllable — it falls out of fitting the freeform data.
  - **Thumb MCP/IP flexion range**, as a byproduct of the same unconstrained trajectory — no separate Phase-3-style scripted per-joint thumb test is planned, on the same logic used to simplify this phase already: a natural comfortable movement will appear in freeform coverage without needing to be scripted. Worth validating this actually yields clean enough per-joint angle data once real sessions exist (see "Open items" below) — Phase 3's isolated single-joint sweeps for fingers have an easier extraction job than this superposition-of-everything-at-once trajectory does.
- **Completion criteria (coverage-grid detection):** bin the observed data into named regions rather than a generic grid — near each other fingertip, near the top of the index finger, and whatever else emerges as meaningful once real sessions are run (this list is deliberately not fixed here). Completion = confidence-passing samples exist in a minimum fraction of named regions, not a fixed duration. Live feedback highlights which named regions are still unfilled.
- **Retry:** a region unfilled despite adequate continued time in the current orientation → re-orient (same two-orientation default and escalation logic as 6a) and continue building on the same retained coverage map, rather than restarting or just waiting longer in a pose that may not be able to see that region at all.

## Completion-state patterns, generalized

Two reusable patterns cover every phase above; a developer implementing `/scan3` needs both, not phase-specific one-offs:

1. **Plateau detection** (Phase 3's full tier, Phase 4, Phase 6a): track a running extremum (min/max angle) across repeated cycles; declare convergence once the last _k_ cycles each fail to extend the extremum by more than a small threshold. Used whenever the target quantity is a single scalar bound approached asymptotically through repetition. Phase 6a adds a false-plateau guard on top of this base pattern (confidence/yield must stay healthy through the apparent extreme, not just the angle plateauing) — worth considering for any other phase where occlusion risk is non-trivial, not just the thumb.
2. **Coverage-grid detection** (Phase 5, Phase 6b): bin a 2D (or higher, or named-region rather than strictly gridded) space into cells; declare convergence once a minimum fraction of cells has been visited with confidence-passing data. Used whenever the target quantity is a _region_, not a single bound, and exhaustive duration isn't itself the goal — even coverage across the space is. Phase 6b's retry logic extends this pattern with re-orientation as an explicit escalation step when coverage stalls, distinguishing "hasn't tried yet" from "camera can't see this from here."
3. **Still-window detection** (Phase 2, Phase 3's comfortable tier, Phase 4's press-contact instants): a shared low-variance-window extraction, either via velocity-thresholding over a freeform hold or via a self-marking physical event (desk contact) — prefer the latter wherever a natural physical event is available, since it's a more reliable segmentation cue than inferring stillness from noisy motion data.

Every phase's segment additionally fails, independent of its specific criterion, if accepted-frame yield (post confidence-filtering) is too low — this is the one universal retry trigger layered under all three patterns.

## Open items, deliberately left unresolved here

- **DIP-vs-PIP coupling is now fit per finger from Phase 3's own data (see Phase 3), not assumed from literature** — but the functional form of that fit (a simple linear ratio vs. something with an offset/dead-zone/nonlinearity near the extremes) isn't settled here, just left as "regress it and see." Worth checking once real per-finger data exists whether a straight line is actually a good fit or whether the relationship needs a richer function, especially for fingers with a very small DIP range where noise could dominate a near-flat fit.
- **The existing `degree: 0 | 1 | 2` per-joint scheme has no slot for a rotation that's a fitted function of two other rotations.** Phase 6b's conjunct-rotation coupling needs a genuinely different representation than every other joint in the model uses — this is a schema/architecture change beyond capture, connecting to `pre-development-work.md` §1's schema work, and should be scoped there rather than assumed to fall out of just changing `degree` from 0 to something else for the thumb's CMC.
- **Phase 6's two-orientation default and false-plateau guard are new, untested design choices**, same caveat as the camera-calibration gesture in "Camera constraint" above — worth checking against real capture data whether they're actually needed/sufficient, not assumed correct because the reasoning behind them is sound.
- **Whether Phase 6b's freeform trajectory yields clean enough per-joint MCP/IP angle data for the thumb** (as opposed to Phase 3's isolated single-joint sweeps for fingers) is an assumption, not a validated extraction result — flagged inline in Phase 6b, repeated here since it's a real risk to the "no separate thumb flexion test needed" simplification.
- **Whether a genuine second (harder-but-still-active) abduction tier exists at all was left as "probably not, single tier is honest,"** not conclusively ruled out — worth revisiting if early `/scan3` data suggests otherwise.
- **Bimanual/interlimb coupling risk** was the reason bilateral capture was dropped in favor of one-hand-at-a-time for Phases 3–6; this hasn't been empirically tested, only reasoned about. If session time becomes a real problem, it's worth the empirical comparison (isolation quality bilateral vs. sequential) floated earlier before reconsidering. Phase 2 is exempt from this concern specifically because it has no isolation to protect — worth double-checking that reasoning holds once real sessions exist, rather than assuming a phase with no _instructed_ isolation target is automatically free of any bimanual interaction effect on the resting angles themselves.
- **Phase 5's coverage-grid resolution** (how coarse the bins can be before the boundary becomes useless) is explicitly the same open question `scanning.md` already flagged and it isn't resolved by unifying drag/block into one phase — still needs empirical tuning.
- **The camera-orientation calibration gesture (see "Camera constraint" above) is a new, untested idea, not a validated technique.** Whether users can reliably form a genuinely orthogonal three-finger pose (versus an approximately-perpendicular one that introduces its own error into the reference frame), and whether the resulting frame meaningfully improves later completion/quality scoring versus just accepting whatever noise an unknown camera angle introduces, are both open questions worth checking against real capture data before leaning on it.
- **`E[i][j]` is measured from slow, deliberate exploration (Phase 5), and is assumed — not validated — to also hold during fast, real-keystroke-speed motion.** This is currently accepted as the only practical option, since there's no fast-tapping capture phase to check it against. Dynamic/reflexive coupling during a rapid strike could plausibly differ from what a slow freeform sweep reveals. This assumption is load-bearing for the accidental-activation check proposed in `key_point_selection.md` (does pressing one key drag a neighbor's finger far enough to trigger its key too) — worth revisiting with an actual fast-tapping trial if that check's predictions turn out to be unreliable in practice.
